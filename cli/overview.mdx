# updates.page CLI

The `@updatespage/cli` package lets you create and publish posts from your terminal — perfect for release scripts and CI pipelines.

<Note>
  The CLI uses the updates.page API, which is available on the **Pro** plan and
  above — and for the first **14 days** of any new account on the Free plan, so
  you can try publishing from your terminal or CI before you pick a plan. See
  [Authentication](/api/authentication).
</Note>

## Installation

Requires **Node.js 22.13+** (23.0–23.3 are not supported; 23.4+ is).

```bash
npm install -g @updatespage/cli
```

## Signing in

```bash
updates login
```

This opens your browser and asks you to approve the CLI. On a machine without a browser — an SSH session, a container, CI — it detects that and shows a short code you enter from any other device.

For unattended use, pass a token on stdin or in the environment so it never lands in your shell history:

```bash
updates login --token - < token.txt
# or
UPDATESPAGE_TOKEN=... updates list
```

Tokens are stored in `~/.updatespage/credentials.json` with `0600` permissions. `updates logout` revokes the token on the server, not just the local copy.

<Tip>
  Keep separate accounts side by side with `--profile`: `updates login --profile work`, then `updates list --profile work`.
</Tip>

## Commands

| Command | What it does |
|---------|--------------|
| `updates publish [id]` | Create and publish a post, or publish an existing draft |
| `updates draft` | Create a post without publishing it |
| `updates update <id>` | Change fields on an existing post |
| `updates unpublish <id>` | Revert a published or scheduled post to a draft |
| `updates delete <id>` | Delete a post permanently |
| `updates list` | List your posts (`--status draft\|published\|scheduled`) |
| `updates get <id>` | Show one post in full |
| `updates categories` | List categories (`create`, `update`, `delete` too) |
| `updates upload <file>` | Upload an image and print its URL |
| `updates login` / `logout` / `whoami` | Sign in, out, and check who you are |
| `updates doctor` | Show the resolved setup and where each value came from |

Run `updates <command> --help` for the details of any one.

### Post fields

`publish`, `draft`, and `update` share these flags:

| Flag | Effect |
|------|--------|
| `--title <title>` | Post title |
| `--content <html>` | Post body (HTML or plain text) |
| `--category-id <id>` | File under a category (ids from `updates categories`) |
| `--summary <text>` | Short summary shown in feeds and embeds |
| `--url <url>` | Link the post to an external page instead |
| `--private` / `--public` | Hide from / show on the public changelog |
| `--cover-image <path>` | Set the cover from a local png/jpg/gif/webp |

```bash
updates publish --title "New: Dark mode is here" \
  --content "<p>You can now switch to dark mode from your profile menu.</p>"
```

### Scheduling

```bash
updates publish --title "Big launch" --content "<p>Soon</p>" --at 2026-09-01T09:00:00Z
updates publish 1nJKvB --at 2026-09-01T09:00:00Z
```

`--at` takes ISO 8601. A value without a timezone is read as local time.

## Using in CI

Store a token as a secret and read it from the environment:

```bash
export UPDATESPAGE_TOKEN="$UPDATES_PAGE_TOKEN"
updates publish --title "v2.4.0 released" --content "<p>See the full notes on our changelog.</p>"
```

<Tip>
  Create a dedicated **machine key** for CI in **Settings → Developer → API Keys** — it is limited to posts, categories, uploads, and imports. See [Authentication](/api/authentication).
</Tip>

## Scripting

<Tip>
  Driving this from a coding agent? [Using updates.page from an agent](/agents)
  is the whole loop on one page, including when to draft rather than publish.
</Tip>

Every command takes `--json`, which puts structured data on stdout and nothing else — progress and prompts go to stderr:

```bash
updates list --status draft --json | jq -r '.posts[].id'
updates upload shot.png --json | jq -r .url
```

Failures exit with a code that says what went wrong:

| Code | Meaning |
|-----:|---------|
| `0` | Success |
| `1` | Anything without a more specific code |
| `2` | Usage — unknown flag, missing argument, bad value |
| `3` | Configuration problem |
| `4` | Not signed in, or the token was rejected |
| `5` | Network failure or server error |
| `6` | The thing you named does not exist |
| `7` | It exists, but is in the wrong state for this operation |
| `130` | Cancelled (Ctrl-C) |

`7` is the one worth handling deliberately: it covers validation failures
(`422`) as well as genuine conflicts (`409`), so it is what you get from
publishing a post that is already live *and* from sending a field the API
rejects. Either way something has to change before the command is worth
running again.

Driving the CLI from an agent? [Using updates.page from an agent](/agents)
has the same table with what to do about each.

## Troubleshooting

```bash
updates doctor
```

Prints the endpoint, config file, credential store, and where each value came from — a flag, an environment variable, or a default. It exits non-zero if anything is wrong, so it doubles as a CI health check.

<Note>
  **Upgrading from 1.3?** `updates config --api-key` was removed in 1.4 — run `updates login` (or use `$UPDATESPAGE_TOKEN`) instead. Keys saved by 1.3 are not read.
</Note>
